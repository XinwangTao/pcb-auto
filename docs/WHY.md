# 凭什么说这个更好 · An evidence-based comparison

> 这份文档的目的不是说服你，是让你能**证伪我**。
> 每一条主张都附了复算方式；凡是没验证的，我会明写「未验证」。

---

## 0. 先把「更好」定义清楚

「更好」在功能维度上没有意义 —— 芯片支持、层数、封装库，这些都是**广度**，而我只有 33 个设计。
在广度上我不可能赢，也不打算赢。

我主张的「更好」只有一个维度：**可复算性**。

具体说：**你拿到我的任何一个数字，可以在 20 秒内用一条命令自己重算出来，不需要 API key，不需要大模型，不需要相信我的话。**

这件事听起来很小，但它是这个领域里最稀缺的东西。原因见下一节。

---

## 1. 这个领域的通病：演示是可控的，失败率是保密的

AI 做 PCB 的公开材料高度同构：一个漂亮的动图、一块布通的板、一句「AI 现在能设计电路了」。
然后没有然后了 ——

- **没有分母**：「成功生成了 PCB」——生成多少块？试了多少次？失败的那些长什么样？
- **没有时刻**：这个结论是哪一版模型、哪一版代码、哪一天跑出来的？
- **没有失败样本**：失败的设计从来不出现在博客里。
- **自评代替独立验证**：「DRC 通过」是流水线自己说的，还是有第二个程序独立测的？

这不是道德问题，是**激励问题**：演示的收益属于发布者，失败率的代价也属于发布者。

所以在这个领域里，「我公开了我的失败率」本身就是一个不常见的行为。

## 2. 我做了哪些别人通常不做的测量

### 2.1 公开失败率，并且**带上分母和时刻**

当前语料（2026-11-26 10:08 +08:00，settle 180 s，重算命令 `node cli/pcb.mjs census --settle 180`）：

| | 数 | 分母 |
|---|---|---|
| 产物目录 | 53 可打样 / 3 有阻断 | 56 |
| 板名 | 42 至少一次可下单 / 2 从未 | 44 |
| 首次重跑就成功 | 36 / 44 | 44 |
| 需要 5 次才成功 | 1 / 44 | 44 |

**并且我明确写了分母为什么会变**：settle 窗口取 0 / 180 / 实时扫描，会得到三个都成立的目录数。
所以「56」不是一个事实，是「在 settle=180、时刻 10:08 下的一个测量」。

绝大多数公开材料连这一步都不做。

### 2.2 把「自评」和「独立闸门」分开，并测量它们的分歧方向

`fabcheck.js` 是一个**独立程序**：它只读 Gerber / Excellon / BOM / PnP 文本，重新解析一遍几何，
自己判断能不能打样。它不看流水线的 `_run.json.ok`。

这两个字段的分歧我做了四格表：

| | fabcheck 可下单 | fabcheck 阻断 |
|---|---|---|
| 自评 `ok=true` | 48 | **0** |
| 自评 `ok=false` | **5** | 3 |

结论：**危险方向 0 次，悲观方向 5 次。** 我把这个结论也公开了，包括「这只是一次测量、不是保证」。

大多数项目只报「DRC 通过」。它们不测自评与独立闸门的分歧，也就不知道自己错在哪一侧。

### 2.3 四层验收，不是一个

`run-all.ps1` 写出的 `_gates.independent.json` 里是六个独立判据：
`pipelineSelfOk` / `verifyArtifacts` / `drcIndependent` / `fabcheck` / `artifactsFormat` / `deliverableDocs`。
交付一致性另有 `verify-delivery.ps1` 的 19 组判据（`PASS 18 / INFO 12 / WARN 2 / FAIL 0 / ERROR 0` 在 `-SkipCensus` 下）。

关键在于**它们是不同的问题**，不是同一个问题的四种问法。

### 2.4 公开自己文档里的错

两位 fresh-context 审计员查了交付物：
- 网页审计：278 个数字 → 265 对 / **6 错** / 4 口径可疑 / 3 不可复算
- README 审计：95 条断言 → 78 对 / **7 错** / **7 过期** / 3 分母不明

我**没有**偷偷改掉这些错。`交付-README.md` 的「已知限制」里逐条列出了这 13 个错，并且写了理由：
「改生成器要重跑整套产物并重新验证，时间不够；**写清楚它哪里不可靠比悄悄改一半安全**」。

> 一个编造的数字之所以危险，不是因为它错，而是因为它看起来跟真的数字一模一样。

### 2.5 一个 227 KB 的错误账本

`out/_build-ledger.md`（227,923 B）记录了整晚的自我翻车：patch 装上又回滚、重试阶梯让结果变差、
census 的 settle 窗口比一次尝试还短导致测到了上一次的残留、`os.kill(pid,0)` 在 Windows 上其实是 `TerminateProcess`。

这份东西的用处不是自嘲。它是**给下一个做类似系统的人的负面清单** ——
这些坑每一个都是花了几十分钟才定位的。

## 3. 跟别人比

### 分类，不排名

| 类别 | 代表 | 你该在什么情况下选它 |
|---|---|---|
| **代码即电路（声明式）** | **tscircuit** | 你愿意写 TypeScript/React，要一个能跨平台跑、有社区、能 npm 装的开源全栈 |
| **代码驱动 EDA 库** | **skidl**、**KiCad `pcbnew` Python API** | 你已经用 KiCad，要 20 年生态、真制造验证、脚本化 |
| **商业 AI EDA** | **JITX**、**Flux**、**Celus**、**Avid/Jacobi** | 你要真交付、有支持合同、愿意付钱 |
| **AI 检测/辅助** | **DeepPCB**（缺陷检测）、Altium 自动化 | 你的问题不在设计生成而在别的环节 |
| **「LLM + KiCad」实验** | Anthropic/OpenAI 的博客式尝试 | 你想看能力上限的定性演示 |
| **本项目** | pcb-auto | 你要**中文自然语言入口** + **一个可复算的失败率** + **一个独立 DFM 闸门** |

我搜了两次没找到同类项目公开语料级失败率，这只说明我没找到，不说明我是唯一。

### 我明确不如别人的地方

写清楚这些，比写十行优势更有用：

1. **没有一块板被真正制造过。** 这是我最大的硬伤。所有「可打样」都是文件层面的判断。
   一块 Gerber 通过所有离线检查，仍然可能因为阻抗、EMI、热设计、器件选型而出问题。
   KiCad/JITX 有真实量产案例，我没有。
2. **只支持一个 EDA 厂商**（嘉立创 EDA）和**一个操作系统**（Windows）。这是工程债，不是特色。
3. **只有 33 个设计。** tscircuit 的注册表规模比我大几个数量级。
4. **没有社区、没有 npm 包、没有 playground。** 你装它要手动配。
5. **失败的处理方式是「重试更大的板框」，而实测这个策略经常让结果更差。**
   这不是设计，这是没设计。
6. **文档里有 13 个已确认的错误没修**，只是公开了。这比隐瞒好，但比修好差。

## 4. 那凭什么说「更好」

因为**在「你能自己验证我」这个维度上，我没有对手**。具体是三条可执行的事实：

```bash
# 1) 20 秒重算整张通过率表（不需要 API key、不需要模型、不需要联网）
node cli/pcb.mjs census --settle 180

# 2) 逐块板复算可下单性（退出码就是答案）
node cli/pcb.mjs fabcheck examples/d1

# 3) 复算交付一致性（19 组判据，包含跨文件对账）
pwsh -NoProfile -File verify-delivery.ps1
```

而且这三条命令**同时**会重现我的失败：`examples/d1` 会返回 `exit 1`（一条已知误判的阻断），
`census` 会告诉你 3 个目录打不了样，`verify` 会打印那 2 条 WARN。

**一个能让你看到失败的演示，比一个只让你看到成功的演示更可信。**

## 5. 别人可以从我这里拿走什么

这是我唯一希望被借鉴的部分 —— 都不是技术，是习惯：

1. **把「分母」变成必填字段。** 任何通过率不写分母就是宣传。
2. **让检验者与被检验者分离。** 自评 `ok` 不能当验收结论；要有一个只读产物、不读日志的独立程序。
3. **测分歧的方向，不只是有无分歧。** 「自评说通过但其实不行」和「自评说失败但其实行」
   是完全不同的两个 bug，危险程度差一个数量级。
4. **锚点要锚稳定子串，不要锚整句散文。** 我把一条断言锚在生成出来的整句话上，
   文案一改断言就自己红了。
5. **让量具能失败。** 只在好样本上跑一遍不算验证 —— 要故意把生成器改坏，看断言红不红。
6. **把两个不同的数字起成不同的名字。** `ok` 和 `orderable` 不是同一个问题；
   同一个键名服务两个问题时，两边的统计都会错。
7. **公开你的错误账本。** 它比你的成功记录更能让别人少走弯路，也更难被反驳。

## 7. 一句话结论

**如果你的目标是尽快拿到一块能用的板，去用 KiCad 或 JITX，别用这个。**

**如果你的目标是搞清楚「AI 全自动做 PCB 现在到底行不行、行到什么程度、失败率多少」，
并且要求这个答案可以被你自己重算 —— 这个项目是目前少见的、愿意把失败率连同分母和时刻一起交出来的样本。**
