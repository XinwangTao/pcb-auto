### `d0076935fd7b`：修 `routeState=TIMEOUT` 误杀干净板

证据样本 `out\AI_RP2040_系统_15pqy38-20261126-010233`（441.3s，`ok=false`）：

| 字段 | 值 |
|---|---|
| `drcPassed` | **true** |
| `drcLeafCount` / `drcTotalCount` | **0 / 0** |
| `errors` / `mismatches` | 0 / 0 |
| `outlineOk` / `imported` / `layoutState` | true / true / completed |
| `exportsOk` / `exportsTotal` | 6 / 6 |
| `pourRebuildOk` / `pouredCount` | true / 2 |
| **`routeState`** | **`TIMEOUT`** ← 唯一异常 |

- 根因：`routeState` 是**布线器作业**的自述（"作业怎么结束的"），闸门要问的是「板子通没通」。
  两者在后续阶段之后会**分叉**——布线循环以 TIMEOUT 结束，但循环**之后**的 `stitchGaps` /
  `fixClearance` / `patchDrc` 仍在补铜改线，最终 DRC 看到的才是成品。
  文件里 L1232 已有一次校正，但它留在**循环内部**，所以循环之后修好的断连它看不见。
- 修法：在最终判定处（`computeOK` 之前）加一段，**只在最终 DRC 证明零违规时**才恢复。
- 为什么安全：最终 DRC 的零违规**同时覆盖间距与断连**；真有断连必然产生 `Connection Error`，
  `drcPassed` 就不会是 true、两个计数也不会是 0 ⇒ 这条通道不可能放过坏板。
- 边界：`drcTreeUsable===true` 必须成立（空树/读不懂的树一律不算干净，与 L3648 兜底同口径）；
  `routeState` 只认 `TIMEOUT`/`budget` 两个"作业没收敛"取值，`failed`/`error` 之类不许被抹平。
- 记账原则：**`routeState` 保持原始观测不变**，恢复与否单独落 `routeRecovered` 字段，两件事不混
  （同一个字段承载两种语义，正是 `ok` 漂移过一次的原因）。
- 影响面：3 次 `TIMEOUT` 里 **1 次**会被恢复（另 2 次 leaves=46/75，是真违规）。
- 时序佐证：成功样本 57 份 p50=104s / p95=252s / **最大 255s**；TIMEOUT 全在 432–441s，两群分得很开。
  且**没有任何失败样本超过 530s 预算** ⇒ 加预算无用，别去动 `invokeTimeout`。

### slotKeepout 是否真的在看对地方（已部分判定）
- `f8e074286a64` 的填充普查首发于第 2 轮 `d1-sht30`，结果：
  `slotKeepout = {found:0, ..., fillCensus:{1:0, 2:0, 12:0, 15:0, 16:0, 17:0}, censusEmpty:true}`。
  ⇒ 对**这块板**，"`found:0`" 已被判定为"板上确实没有任何填充"，**不是**层筛选写错。
  这正是补丁的目的：把含糊的 0 变成可判定的 0。
- **但仍有一个未判定的高风险**：`_d12-holepairs.md` 第 8 条实测 J1 的槽是
  **DIP 焊盘 + `HOLE_SIZE 31.496 / HOLE_LEN 59.055`**（`FlyingProbeTesting.json`），
  **不是 Fill**。而 `slotKeepout` 是按 `pcb_PrimitiveFill.getAllPrimitiveId(12)` 找的。
  若 d12 也报 `censusEmpty:true`，则说明**盯错了元件类型**，整套禁布区对 USB-C 槽孔无效，
  必须改按"带 `HOLE_LEN` 的 DIP 焊盘"取几何。等 d12 的第 2 轮日志判定，不先改代码。

#### 判定结论（06:47，**方向作废**）

d12 第 3 轮四次尝试全部 `censusEmpty:true`。语料级量化（250 份日志 / `_log*.json`）：

| 指标 | 结果 |
|---|---|
| `slotKeepout` 事件 | 123 次 |
| `found === 0` | **123 / 123 = 100%** |
| `found > 0` | **0 次** |
| `skippedBig` 累计 | **0** |
| 带 `fillCensus` 的事件 | 99，**其中 99 次全零** |

**决定性的那一行**：同一份日志里

```
fillCensus : {"1": 0, "2": 0, "12": 0, "15": 0, "16": 0, "17": 0}   ← "全板没有任何填充"
pourRebuilt: {"poured": 2}                                          ← 两层铜都在
```

`d12` 的 `USBC_Power_ESD-20261126-053328` 四次尝试、连同 03:36 那次，**每一条**都是这个形状。

⇒ **`pcb_PrimitiveFill.getAllPrimitiveId()` 对任何层都返回空**，包括板上确实有铜的 1/2 层。
原因是本流水线自己造的铜是 `PCB_PrimitivePour`（覆铜），**不是 `PCB_PrimitiveFill`（填充）**；
而 OLED / USB-C 封装内部的槽区既不是 Pour、又不可枚举（与"没有 API 能枚举器件内部图形"同一条）。

**所以这不是"层筛选写错"，是"普查查的对象根本不是槽区所在的类"。**
`f8e074286a64` 那次"只增记录"的意图是"把含糊的 0 变成可判定的 0"，
**结果相反：它把一个未知渲染成了 0，让 0 看起来成了结论**——正是本夜反复吃的那一类亏。

**因此**：
- **不要再调面积上限 `sArea > 640000`**：它在面积判断之前就已经 `found:0` 了，改上限不产生任何行为变化。
- **不要改按"带 `HOLE_LEN` 的 DIP 焊盘"取几何**：`_d12-holepairs.md` 第 8 条那个 DIP 焊盘是 **J1 的 USB-C 槽**，
  d12 的失败类别里没有 `Slot Region`（是 `Connection Error | Track`），而真正报 `Slot Region` 的
  d13 / `a0-gen` 的槽在 **OLED 模组封装内部**，两者不是同一件事，换对象仍然取不到几何。
- 结论：**OLED 这一类（d13 三次、e-h、a0-gen）在当前 pro-api 公开能力下没有可用的自动修法**，
  唯一诚实的处置是把它作为已知限制交付，而不是继续试。

### 为什么必须重渲染（实测，非推测）
- 现象：`打样检查清单.md` 写「独立校验门：未验证（未找到 _gates.independent.json）」，
  而该文件**就在同目录**且六道门全 true。**8/8 命中，含 finalOk=true 的板。**
- 根因是**生成顺序**，不是文案：文档在流水线内生成，门禁在 `run-all.ps1` 的 `finally` 才写，
  文档生成时那文件确实不存在 ⇒ 措辞是诚实的，位置是错的。
- 修法：门禁落盘后，若 `$docsOk -eq $true` 就再跑一次 `make-deliverables.py`。
  只在 `$docsOk` 为真时重跑 —— 否则文档步骤本身失败时重跑会凭空补出文档，
  而门禁里记着 `deliverableDocs=false`，反而制造新的不一致。
- 实测代价 0.44s/次；只改动「门禁行」与「面积交叉校验行」，行尾 CRLF 与编码不变。
  失败板正确显示 `0 / 5 项为 true`，通过板 `6 / 6 项为 true（六项全列）`。
- **已实测生效**（不是推理）：`SHT30_I2C_TempHumidity-20261126-031806`（第 2 轮，221.0s PASS）
  的 `打样检查清单.md` 门禁行 = `6 / 6 项为 true（pipelineSelfOk、verifyArtifacts、

### `5fa55a1feb1f`：三个"全绿但不可用"的缺陷（实测驱动）

用 20 个自然语言想法做黑盒泛化测试，发现编译器能**拒绝**（12/20 明确报错，理由具体到器件名），
但成功产出的板里有电气错误。三个缺陷逐一定位：

**① 关键词漏「充电」**（L46 原 `/充电管理|锂电|电池|charg|tp4056|lipo|li-ion/`）
- 目录里 TP4056 的 tags 早就写了 `太阳能/光伏/mppt`，而关键词规则只认「充电管理」——两处不一致。
- 后果：想法「太阳能充电的温湿度记录仪」只命中二极管、不命中充电 IC ⇒ 二极管被串到
  **不存在的** `VIN_CHG` 入口上，网表出现 `5V = {D1.1}` 单脚网络，被 `finish()` 护栏拦住（exit 1）。
- 影响面已核：19 个现有 `designs\*.json` 里"含充电但不含充电管理"的只有 1 个
  （`gen-做一个-TP4056-锂电池充电板…`），而它已含 `TP4056/锂电/电池` 三个词 ⇒ **对现有设计零影响**。

**② 二极管落点可以是空网**（`diodeOut`）
- 旧写法无条件串到 `chgSupply`，而 `chgSupply` 在"没有充电管理"时停在 `'5V'`，
  可那块板上没有任何器件往 `5V` 供源 ⇒ 悬空。
- 改成：有充电 IC → 充电入口；无充电 IC 但有 LDO → LDO 的 5V 输入；两者都无 → 系统电源 `VDD`。

**③ 传感器模块可以没有任何对外连接器**（最严重，最隐蔽）
- 想法「带 LDO 稳压和电源指示灯的 SHT30 温湿度模块：5V 输入 → AMS1117-3.3 → 3.3V 给 SHT30…」
  **不含"排针/引出"**，于是 `if (wantsHeader)` 整块被跳过。实测生成的板：
  ```
  5V  = {U2.3(VIN), C2.1}              ← LDO 没有电源来源，板子无法上电
  SDA = {U1.2, R1.1} / SCL = {U1.3, R2.1}  ← 只连上拉电阻，外部读不到
  排针/连接器数量 = 0
  ```
- **网表自洽**（每网 ≥2 引脚，单脚护栏看不见）、DRC 会过、六道闸门全绿，**却完全不能用**。
  比"少装一个器件"更隐蔽：网络是完整的，只是**通不到板外**。
  而这个设计就在循环的设计集里，每轮都被构建并报 PASS。
- 修法：模块类配方（传感器/纯分立/充电板）**强制带连接器**；只有 `sysFromBatt`（系统真的
  从电池取电）才把 `VBAT` 引到排针 —— 旧 `sigs` 在"有 LDO 但没电池"时引 `VBAT`，
  那一补连接器就会立刻多出单脚网络（同一个 bug 的两半，必须一起修）。

### 加了 BGM 之后成片被自己判死：真峰值必须压，且必须压在 `amix` 之后（`b2c80988b90d` → `a3050569d016`）

第一次用 BGM 出片，`verify-film.ps1` 直接判 `FAIL true_peak=-0.52 dBTP > -1.0`，`ship.ps1 exit=6`。
**不是人声超标** —— 单独量人声是 `I=-16.93 / TP=-4.50`，完全合规。是 `amix=inputs=2:normalize=0`
把 BGM 的能量**加**上去，峰值就抬起来了；而 `loudnorm=I=-16:TP=-1.5` 只挂在 `[0:a]` 这一路，
它管不到后面的求和。**一道只管单路的 loudnorm，不能给多路混音兜底。**

修法：限幅器挂在 `amix` 之后，`alimiter=limit=0.794:level=false`。
- `level=false` 是关键：`alimiter` 的 `level` 默认 `true`，会把输出整体拉到 limit 电平
  （等于又做一次归一化），`false` 才是"只削峰、不抬底"。
- `limit=0.794` = `-2.0 dBFS`：从 `voice_v7.wav` 重放时 base `TP=-1.00`，而成片比重放高
  `0.48 dB`（Remotion 那次 aac 编码会抬峰），留 1 dB 余量刚好。
- 响度几乎不动：`I -15.77 → -15.84`，仍在 `-16±1` 内。

**这条闸门是有价值的，别为了过闸去放宽它**：`TP > -1.0` 的片子在部分平台会削顶失真，
而"削顶"在缩略图和母版上一眼看不出。

SWCLK=U1.24+H1.6、SWD=U1.25+H1.5、RUN=R1.2+U1.26+H1.4、5V 3 点、3V3 16 点、GND 12 点，

### `accept.ps1` 把"测过但没过"写成"没测"（`f5b9a9925a30` → `70b5ba1579bb`）

5 条"测过但未通过" + 1 条"未执行/无记录"。**退出码和判决一个字没变**，只是归因对了。

### d11 布不通不是板子的问题，是**一次慢 FAST 变体把保底轮的预算吃光了**（`ebbc340eb05f`）

我此前的记录写着"`routeState=TIMEOUT` 在语料里 0/3"，那是错的。按 513 次 `route` 事件重算：

| iter | n | TIMEOUT | 均值 | 最大 |
|---|---|---|---|---|
| 0（FAST） | 131 | 1 | 9,517ms | **317,395ms** |
| 1（FAST） | 127 | 0 | 1,456ms | 6,054ms |
| 2（FAST） | 127 | 0 | 1,475ms | 8,333ms |
| 3（**COMPLETION 保底**） | 128 | 2 | 20,592ms | 133,617ms |

唯一的 **317s TIMEOUT 与 207s completed 都是 d11（Crystal RTC）**，比第二名慢一个数量级。
后果是连锁的，`fail-d11-crystal-rtc-20261126-015151-r2.txt` 的实测量：

```
route → {"iter":0,"state":"TIMEOUT","ms":317395}
```

然后 `capRaw = left() - 180000` 只剩几百毫秒 ⇒ 之后每个变体都 `routeBudgetSkip`；
`left() < 240000` 又把 `iter3` 挡在门外 ⇒ **COMPLETION 保底轮一次都没跑**，
板子带着 27 处断连被判死（`Connection Error | SMD Pad=20; | Track=1; | TH Pad=6`）。

而 L1179 早就写着："**每一次成功都是 iter 3（COMPLETION 保底轮）把 stillUnconnected
打到 0，且只花 21~31 秒**"。也就是说：最贵的那个尝试有优先权，最便宜最可靠的那个没有。

**修法**：`fastCap = isStrong ? 900000 : 120000`。孤立模拟两种预算算术：

```
现状：iter0/v0 wait=317000 → TIMEOUT (left=180000)
      iter0 全跳过 / iter1 全跳过 / iter2 全跳过 / iter3 全跳过   ← 保底轮从未运行
修法：iter0/v0 wait=120000 → TIMEOUT (left=377000)
      iter0/v1 wait=120000 → TIMEOUT (left=257000)
      iter0/v2..iter2 跳过（routeBudgetSkip capRaw=77000）
      iter3/v0 wait=77000 → completed 25000ms (left=232000)     ← 保底轮跑到了
```

120s 这个数不是拍的：两次 FAST 超时 = 240s，加收尾 180s 仍在 530s 预算内，
且此时 `left≈257s > 240s`、`capRaw≈77s > capNeed 45s`，保底轮**必能**进入。
正常 FAST 只要 3.6~30s，120s 是 4 倍余量，对通过中的 25 个设计零影响。

同一个坑的一般形式：**预算按先到先得分配，而各尝试的可靠性是倒序的** ——
最不可靠的那一步拿到最大配额，最可靠的那一步被挤掉。

**现场复现（不是模拟）**：`Crystal_RTC_Clock-20261126-051342` 的
`_log-3-expand-1.25x-retry.json`（05:22 启动，**早于** 05:23 落盘的 `ebbc340eb05f`，
所以跑的是旧代码）把机制完整演了一遍：

```
route            iter0 completed 173136ms     ← 又是一次慢 FAST（173s）
routeBudgetStop  iter1 leftMs=219415 done=1   ← 219s < 240s 闸门，跳过
routeBudgetStop  iter2 leftMs=214080 done=1
routeEscalate    FAST 3 轮后仍有断连，升级 COMPLETION 兜底
routeBudgetStop  iter3 leftMs=208515 done=1   ← COMPLETION 也被跳过
```

`routeEscalate` 明确宣告"要升级保底轮"，而**下一行就把它跳过了** —— 这就是
"先到先得吃光预算"最赤裸的形态：一个慢 FAST 花掉 173s，之后每一档都过不了闸，
包括那个自述"每次都靠它才成功、只花 21~31s"的保底轮。
结果 `_run-3` 的 `drcLeafCount=7`。

修法会在 120s 处掐断那个慢 FAST（对 25 个正在通过的设计零影响，它们只要 3.6~30s），
留下 ≈377s，使三次迭代都能通过 `left() >= 240000` 与 `capRaw > capNeed` 两道算术。
**这条实测取代了原来的孤立模拟，成为该修法的首要证据。**

### `idea2design.js`：充电输入没有入口（`7eebf0152c04`）

### 失败面普查（按尝试而非按设计计数，2026-11-26 05:3x）

- 只取孔 → 小于铜（可能压焊盘铜）；
- 只取焊盘盒 → 可能远大于真铜（本文件见过 100×100 的盒对 31.5×59.1 的孔）；

### 【误判纠正】`clearanceReverted` 的 `deleted≠restored` 不是缺陷，是两把不同的尺子

我差点去修一个不存在的问题。全语料 28 次回滚，`deleted == restored` **0 次成立**，
看起来像"回滚从来没有真正还原"——但这是**单位不可比**：

| 字段 | 数的是什么 | 代码 |
|---|---|---|
| `deleted` | 本轮**删掉的图元个数**（绕行时新建的多余线段 + 被删的过孔） | 删除循环 |
| `restored` | **线 `modify` 还原成功次数**（把原 Track 的 `endX/endY`/`lineWidth` 改回去） | L2570-2571 `rb.restored++` |
| `viaRestored` | 过孔 `create` 回来成功次数 | L2561 `rb.viaRestored++` |
| `fixedGivenBack` | `restored + viaRestored`，**这才是与"一处修复"同单位** | L2576 |

铁证（单位不可比而非还原失败）：
- `Crystal_RTC_Clock-20261126-001315 _log-1`：`del=2 rest=3` —— 还原**多于**删除。
- `Crystal_RTC_Clock-032420 _log-3`：`del=4 rest=11 from=50 to=17`。
- d13 尝试 2（`19ptbuz-055041`）：`del=4 rest=2 viaRest=0 fixReq=2 givenBack=2` ——
  2 处修复各"撤 2 条新建线段 + 改回 1 条原线"⇒ `deleted=4, restored=2` **完全对得上，回滚是完整的**，
  且该次 `clearanceRevertOk: true`、`dangling: []`。

**要读的是 `fixedRequested` ↔ `fixedGivenBack`**，不是 `deleted` ↔ `restored`。
按这个口径复查：大多数回滚 `givenBack == fixReq`（完整）；真正不全的case（如 d13 尝试 1
`fixReq=1 givenBack=0`）都已经被 `clearanceRevertOk=false` + `clearanceRevertDangling` 记下来了，
且 8 次 `clearanceRevertOk=false` **全部**落在本来就失败的尝试上（0 个假通过）。

⇒ **不给它加闸门**：一个区分力为 0 的条件不该升级成判据。
（教训：先确认两个计数器是否同一单位，再把它当分子分母。）

## 2026-11-26 06:30 之后新增的三条结论

### 一、录制哨兵 `.record-on` 的真实代价是 **+106.5 s / 次尝试**，不是注释里写的 +10 s

`run-all.ps1` L26 有一个哨兵文件旁路：`.record-on` 存在就强制 `-Record`。作者注释说"约 +10 s"，
实测差了 12 倍：

| 对照 | 同一设计 / 同一策略位置 | 耗时 |
|---|---|---|
| 哨兵存在（04:48:39 之后） | `SHT30_Header8` smart-fit | 190–285 s |
| 哨兵存在 | 其它小板同类 | 231–284 s |
| 哨兵不存在（哨兵创建前已起跑的那次） | 同板同策略 | **Δ = +1.3 s** |

- `out\frames\` 最新写入停在 **06:30:21**，之后 `d5`/`d6` 均无新批次 ⇒ 录制确实关了。
- 第 3 轮整体从"1.78× 于第 2 轮"回到正常速度，预计 **07:30 前**跑完 30 个设计。

这条同时纠正了一个错误归因：**第 3 轮慢不是机器退化，是录制**。

## e-b-led8-rain 为什么四次都 45 条

`AI_纯分立_17py4dl-20261126-064538`，17 器件 / 54 连接 / 设计板 1400x1000。四次尝试 `leaf=45` 一字不差，
`byType` 全是 `Connection Error | SMD Pad`，`byNet {GND:12, 5V:9, LED_A1..A8 各 3}`，
`routeIter {iter:3, stillUnconnected:54}` —— **54 个焊盘一个也没连上**。

板**确实扩了**且 `ok:true`：`outlineExpandPlan {need:[2570,902], result:[2570,1836]}`，`outline.ok=true`。
但布局跨度 `bbox [41,-1031,2491,-250]` / `span [2450,782]` **四次完全不变**，连板框从 1400 改成 1750 都不变。

⇒ 两件事：
1. **`outlineFit` 的扩容发生在 `autoLayout` 之后，而扩容不会重跑布局。** 所以"框放大到 2570"只是把已经排好的器件围起来，
   排布本身仍是按 1400 的板算的。这与 L780-784 那条注释（收缩要交给外层用更小初始板框重跑）是同一个道理的另一半，
   但**扩容这一侧没有对应机制**。
2. **自愈链的固定 1.25 倍够不到这块板**：1400→1750→…每次都只到 1750，而布局跨度 2450 需要 ~1.75 倍。
   三次 retry 全在同一尺寸上重复，所以四次结果字节级相同。这不是抖动，是**阶梯步长小于需求**。

未改代码：e-* 是自造设计，交付集是 d1-d13 + a0/a1-gen；在 07:11 动 `run-all.ps1` 的 `$healPlans`
只会让失败设计更慢、把第 4 轮推到 a0-gen 之后。**记为已知限制。**

### 处置（07:12）：改设计，不改流水线

`e-b-led8-rain.json` 的 `boardWidthMil` 1400 → **2600**（8 个 LED 串一行，实测跨度 2450 + 两侧各 60 边距 = 2570）。
只改这一个键，其余键逐个断言相等；`audit-design.js` 仍 exit 0（17 器件/54 连接/10 网络）。

为什么改这里有效：`run-all.ps1` 只在两种情况下覆盖声明板框 ——
`$baseArea > max($estArea*2.2, 5x5)` 时预剪、`$baseArea < $estArea*0.75` 时预放（L495-503）。
e-b 的 `$estArea = 17*55000 + 54*9000 = 1,421,000`，覆盖区间是 `[1,065,750, 3,126,200]`；
1400x1000=1,400,000 与 2600x1000=2,600,000 **都落在区间内**，所以声明值会原样使用。

为什么不改 `$healPlans`：改 1.25 的倍数会让**每个**失败设计都多烧一轮（今晚失败设计平均 ~1000s），
换来的只是 e-* 这类自造设计。而修设计文件是零风险的（不需要 EDA 锁，`audit-design.js` 可离线验）。

### 写核查器时踩的两个坑（都是"读法错"，不是"文件坏"）

- **`PnP.csv` 各目录编码不一**：新目录 UTF-8 BOM，老目录 **UTF-16**。按固定编码读，在某个目录上直接抛
  `UnicodeDecodeError: 0xff in position 0`。必须按 BOM 嗅探。**这类异常是量具的错，不许当成被测对象的缺陷。**
- **设计器件字段名是 `des`**，不是 `designator`/`ref`。按猜的名字读会得到"设计 0 个器件"，
  于是"三方差一致"必然失败、还会把全部位号报成"缺失" —— 一个纯属编造的失败。
  修法是**先打印真实结构再写判据**（`json.dumps(components[0])` 一行就解决）。

### 【我自己的量具 bug】Gerber 板框解析把文件头当成了坐标

第一版对整个文本 `re.findall(r"X(-?\d+)")` 取极值。文件头是 `%FSLAX45Y45*%`，
于是 **`X45`/`Y45` 被当成坐标**。当板上所有 Y 都为负时，那个 `+45` 把高度撑大：
e-b 真实 1836 mil 被算成 **3395 mil**（差 1.85 倍）。
Y 有正坐标时误差可忽略，所以这个 bug **只在"Y 全负"的板上显形** —— 最容易漏掉的那一类。

修法：只从真正的坐标块 `X(-?\d+)Y(-?\d+)D0[123]\*` 取极值。
修后 e-b 得 2570x1836，与 `outlineExpandPlan.result [2570,1836]` 精确吻合。

⇒ **本文档早先"190/191 板框一致"的结论仍然成立**（那批板 Y 有正坐标，bug 未显形），
但那个数字是**在未修的秤上**得到的，修后重跑同样一致，结论不变、证据已换。

### 顺带确认：`_run.json.boardWidthMil` 是**参数**不是**出货板框**

e-b 的 `_run.json` 记 1750x1250，实际 GKO 是 2570x1836（`outlineExpandPlan` 扩到 2570）。

### 附带修掉一个量具 bug（这次又是我自己的）
统计钻孔数时用 `^X-?\d+Y-?\d+$`，而 Excellon 坐标带小数点（`X23.44565Y-28.30372`），
`\d+` 匹配不到 → **把所有板都数成"0 个钻孔"**。
真值：`Drill_PTH_Through.DRL` **56 孔 / 2 把刀**（0.3048mm、1.0mm），
`Drill_PTH_Through_Via.DRL` **48 孔 / 1 把刀**。

## 分母在自己脚下缩水：自动清理删掉了 240 个产物目录（08:36）

**现象**：上一轮刚跑通的一键复核全绿（226 个目录、221 个可打样），
过了 5 分钟再跑，同一个工具报出 **55 个目录、53 个可打样**，页面也少了一张表。
第一反应是「工具坏了」。不是。

**根因**：`run-overnight.ps1` L276 有 `if ($round % 3 -eq 0)`，
每 3 轮结束就调一次 `scripts\cleanup.ps1 -Apply`。该脚本的保留规则是
**「最近 40 个目录 + 每个设计名最新 1 份」**，外加 EDA 工程只留最近 10 个。
第 3 轮结束时开场日志白纸黑字：`[cleanup] 已删除 240 个`、
`已删除 245 个 AI 工程（用户自建工程未触碰）`。

**这一条为什么重要**：我此前所有比例都写在「226 个目录」这个分母上。
分母不是常量，它会被一个**定时器**删掉 91%。所以：

- 任何跨目录的比例，引用时必须带上 **as-of 时间 + 当时的分母**；
- 更关键的是**要声明分母为什么会变**。只写「本次统计 226 个目录」不够，
  读者会以为那是全部历史，而实际是清理后的残留；
- 我在页面上加了一条橙色告示，直接写明规则、执行次数、累计删除数，
  并且说清「每个设计只看得到最新那一次尝试」——
  这句话把「做成过几块板」的口径限制也一并交代了。

**顺带修掉的两个隐藏假设**：
原来那段文字写死了「229 个目录的 .GKO 共 63 种尺寸」，
以及点名 5 个越框目录的**目录名**。清理之后这两个都是假话，
其中 4 个被点名的目录已经不存在了。现在改成**从普查 JSON 和磁盘现算**：
`gko_shape_stats()` 数 GKO 个数/尺寸种类/单轮廓比例，
越框表格由 `rows` 里 `fab_exit != 0` 的项现场生成。代码里不再出现目录名。

**教训**：一个数字在你写下它的那一刻是真的，不代表交付时还是真的。
凡是「统计磁盘上有什么」的断言，要么每次现算，
要么把「它会变」这件事本身写进交付物。
告诉读者分母怎么来的、会不会变，比自己重算一遍更有用。

## 全局替换非法转义，把 raw string 和 \n 一起改坏了（08:39）

**起因**：新增的 docstring 里写了 `` `scripts\cleanup.ps1` ``，
Python 报 `SyntaxWarning: invalid escape sequence '\c'`。
我想「把所有非法转义一次性修掉」，于是扫全文件、匹配 `(?<!\\)\\[A-Za-z]`、
在每处前面再补一个反斜杠。`py_compile` 通过，`-W error::SyntaxWarning` 也通过。

**坏在哪**：那个正则**只匹配单个**反斜杠，所以

- raw string 里的 `r"D:\Users\…"` 被改成 `r"D:\\Users\…"`
  —— 原本是多反斜杠会被正确解释，改完路径就多了一层；
- 普通字符串里的 `"\n"` 被改成 `"\\n"` —— 换行变成了字面的反斜杠加 n。

表现是页面还写得出来，但 `结果行 0 / 交叉核查 0 目录`——
两个本该非零的统计变成了 0，因为行切分全错。

**不可逆**：原始文件里**单反斜杠和双反斜杠已经无法区分**，
不可能用规则还原。只能从备份重建。

**教训**：
1. **「修所有 X」这种全局替换，在带转义的语法里几乎总是错的。**
   正确做法是只改报错指向的那一处，改完立刻用它验证。
2. 一个能通过 `py_compile`、能通过 `-W error::SyntaxWarning` 的文件，
   **仍然可以是错的**——语法门只证明它能解析，不证明它语义没变。
3. 我保留的 `F:\cache\temp\md-rs-probe.py` 基线救了我。
   **每次改之前留一份带哈希的副本**，这次不是仪式，是唯一的退路。
4. 从备份重建时，锚点要用 `%r` 打印真实内容再写。
   我第一版锚点写了一个反斜杠、文件里是两个，`count` 断言成 0，脚本当场停住——
   **断言命中数就是防这个的**，它比事后看结果便宜得多。

① 139/79 是尝试级、来源是文件 mtime；

## 独立核对员把「零人工干预」证伪了一半（08:56）

### 它证伪的：不是「没有人」，是「系统没被改过」

它给出五类正面证据，**都不是「没找到」，是找到了**：

1. `_pipeline_rev.txt` 序列 `cc9434430d14 → d0076935fd7b → 4c8021bbfcb4 → 53f3522e3d94 → 46512f7070a4 → c1f0ab2ce915`
   —— 流水线代码在夜间**至少被替换 5 次**，其中末次 `c1f0ab2ce915` 是那个失败后被回退的 pour-retry 补丁。
2. 日志里的「校验 18 项 / 19 项」在 05:01、07:00、07:06 三次跳变。
3. `out\_probe\` 里约 15 个 `*.pre-<哈希>` 备份，时间全落在 05:26–08:09 —— 这是「改前先备份」的动作痕迹，循环不会产生。
4. `designs\` 里有夜间新编译的设计文件，而 `run-overnight.ps1` **从不写 designs**（只 `Get-ChildItem`）。
5. `_accept.json` 里凡 07:00 之后写的都带 `"verifyOnly": true, "pipelineRan": false` —— 事后补的验收。

**这些改动全部由 AI（我）发起，没有人在键盘前。** 所以准确的说法是两句，不是一句：

> **跑板全程没有人类操作**（脚本里没有任何 `Read-Host`/`pause`/stdin 路径，机器结构上无法停下来等人）；
> **但代码和设计文件当晚被改过多次，并当场生效**（循环每次尝试重读 `pipeline3.js`，每个设计重读 `run-all.ps1`）。

把这两句压成一句「全程无人工干预」，会让读者以为系统一成不变。
**「没有人」和「没有变化」是两件事**，前者我证得出（空结果有搜索面），后者我证不出（而且它是假的）。
交付页和 README 都已改成两句话。

### 它顺手挖出的四个真缺陷

这就是为什么比例必须连同它的分子分母一起记，只记百分比等于什么都没记。

### 第四类：小的、纯数值的

- 「产物最早来自 11-25 **白天**」→ 实际是 **00:43**，凌晨。
- 台账「**188** KB，按时间**倒序**」→ 实际 **199 KB，正序**。倒序是错的：我是按追加顺序写的，越往后越新。
- 「一键复核约 **35 s**」→ 实测 **17 s**。

### 一般化

1. **输出是数据，代码是规则。** 想解释一个输出为什么是这个数，只能读代码；从输出反推因果，猜对是运气。
2. **凭记忆复述自己写过的数字，是伪造。** 它比编造更隐蔽，因为我真心相信它。正确做法是 grep，或者干脆写「见台账某节」。
3. **一个我没验证过的全称断言（「全部是同一类」「所有都」「没有例外」），它的反面证据往往就在我手边的同一个 JSON 里。**
4. **比例要连分子分母一起记。** 两个不同的分数可以有一个相同的百分比。
5. 核对员最有价值的产出不是「你错了 9 处」，而是**把这 9 处归成 4 类** ——
   单条错误只能修一次，错误分类能改下一次的写法。

## 同一个键名，两份文件两个意思（09:07）

### 我本来写下的是一句错话

看到核对员的报告，我在 README 里写了「`AI_..._055041` 的 `_accept.json` 写 `drcIndependent: false`，
同目录 `_gates.independent.json` 却写 `true`，**两份记录对同一件事给出相反结论，没有仲裁者**」。

听起来像是「有一处偶发的证据冲突」。我去查了一下，**不是偶发，是系统性的 24/25**。

### 真实结构

两份文件都用了 `drcIndependent` 这个键，但**指的不是同一件事**：

| 文件 | 路径 | 含义 | 实测值 |
|---|---|---|---|
| `_accept.json` | 顶层 `drcIndependent` | **本次验收这一趟**自己有没有独立跑 DRC | **38 份里 0 份 true** |
| `_gates.independent.json` | `gates.drcIndependent` | **流水线**的 DRC 闸是否独立 | 基本都 true |

`-VerifyOnly` 不跑流水线（`pipelineRan: false`），所以第一项**按设计就永远是 false**。
换句话说：那不是证据互相矛盾，是**一个人问了「你今天自己检查了吗」，另一个人回答了「这东西出厂时检查过了」**。

**危害在哪**：两份记录放在同一个目录里、用同一个键名。任何后来者（包括我）把它们当同一件事比较，
都会得出「38 块板的验收证据在打架」这个惊人的、而且**完全错误**的结论。
**同名不同义比数值错误更难发现，因为两个值单看都是对的。**

### 我的判据本身也是 fail-open

第一版检查我写的是 `$g.drcIndependent` —— **`_gates` 里这个键在 `gates.*` 下面，顶层没有**，
所以拿到 `$null`；而我又写了「一侧是 null 就跳过比较」。
结果：**这条判据在它本该报警的地方报了 PASS。**

这是本项目第 N 次同一个病：**一个判据在「取不到数据」时选择了沉默，而不是选择报错。**
正确的默认是「取不到就说不确定」，而不是「取不到就当作没问题」。

### 附带发现

`_accept.json` 的 `allOk = true` 与它 `checks` 里那条 `ok=false` 并不矛盾 ——
`allOk` 不是 `checks` 的聚合，它有自己的一套判据。这也是同名不同类的一个变体：
**一个叫 `allOk` 的字段不一定是「所有 check 都 ok」。**

### 现在的状态

`verify-delivery.ps1` 第 8 组每次都会打印：
`38 份 _accept.json 里值为 true 的 0 份` 与 `25 对里 24 对不同`，并解释这是同名不同义。
判 WARN 不判 FAIL —— 因为它暴露的是**命名与文档问题**，不是板子的问题。
**但从此它不会再静默。**

## 证明一条判据会失败，有时得改生成器而不是改产物（09:07）

### 发现：交付页只讲成功面

`out/交付说明.html` 有 9 个 `<h2>`：证据链、真实操作录像、验收的四个层、想法→可下单的板、离线 DFM 普查、

也就是说：**给别人看的那份网页，一条限制都没有。** 这是最后一类需要修的问题 ——
不是数字错，是**选择性地只呈现有利的那一半**。数字全对，但读者会得到一个错误的整体印象。

### 做法：让限制一节由程序现场算，不手写

新增 `<h2>已知限制与证据缺口</h2>`，6 条，每条的数字都当场从磁盘算：

| 条 | 现场算出来的量 |
|---|---|
| 验收记录有缺口 | `61` 个运行目录里只有 `38` 个存了 `_accept.json` |
| 同名不同义的键 | `38` 份 `_accept.json` 里 `drcIndependent` 为 true 的 `0` 份 |
| 警告≠阻断 | `fabcheck` 共报 `114` 条 warning，流水线不拿它当失败 |
| 尝试级历史已删 | 现存 `_run-N-*.json` 仅 `91` 个，「139 次尝试」不可复算 |
| 历史设计不可复现 | `gen-led.json` 6 器件，当前编译器同句只出 3 器件 |
| 零人工≠系统没变 | 无 `Read-Host`/`pause`/stdin，但代码当晚被改过 |

**为什么必须现场算**：我这一晚上因为把数字写死，返工过三次（台账大小 188→193→199 KB、
「204/203」这个凭记忆的数字、`35 s` vs 实测 `17 s`）。**写死的数字不会报错，只会过期。**

### 证伪这关：改产物没用，得改生成器

我给 `verify-delivery.ps1` 加了判据「限制一节在 + ≥5 条 + 必须含两句关键话」。

想证明它会 FAIL，第一反应是**把页面里的那一节删掉**。做了，结果是 **PASS** ——
因为第 4 组会**重生成页面**，生成器又把这一节写回来了。

这不是判据失灵，是**我测错了对象**：判据看的是「生成器还愿意写这一节吗」，不是「当前这份 HTML 里有没有」。
所以真正有效的证伪是**改生成器**：
把 `make-dossier.py` 里的 `<h2>已知限制与证据缺口</h2>` 临时改掉 → 重生成 → 判据
`[FAIL] 限制一节在  页面没有「已知限制与证据缺口」一节（只讲成功面）`，exit 1。还原后 hash 一致。

**一般化：** 当一个判据检查的产物是**派生出来的**，删产物证明不了判据有效 ——
派生程序会把它补回来。要证伪，必须让**上游**不再产生它。
同样的道理：想验证一个「编译产物不含某字符串」的检查，改产物没用，得改源码。

### 附带确认

- 生成器是**确定的**：删掉一节后重跑，页面字节数与删除前完全一致（`sha256` 相同）。这一点之前没验过。
- `verify-delivery.ps1` 现在 `PASS 14 / INFO 11 / WARN 1 / FAIL 0`，`VERDICT=PASS`。

## 重试不是单调改进：d11 越试越差（09:09）

## 两份交付物给了两个头号数字（09:14）

### 现象

`out/_probe/sync-readme-numbers.py`（新）：README 里 `<!-- 核心数字:BEGIN/END -->` 之间整段由它重写。
输入全是只读量具 —— `fab-census.json` 的 mtime（时间戳）、`交付说明.html`（想法级四个数）、

### 加了判据，然后它自己失效了一次

`verify-delivery.ps1` 新增「跨文件对账」：解析页面的 `30/28/93.3%` 与 README 的同一组数，
不等就 FAIL。**第一次跑就抓到真问题**（正是上面那对矛盾），修好后 PASS。

但同一轮里另一条判据塌了：`关键修正仍在` 原本要求 README 含**整句**
「8 个没有 `_run.json` 的目录被静默排除」。这句话现在由脚本生成，措辞变成了
「所以有 8 个没有 `_run.json` 的目录不在里面」—— **判据当场 FAIL。**

两个教训：
1. **别把判据锚在整句散文上。** 散文一旦从"手写"变成"生成"，措辞就随时会变，
   而判据会以"内容缺失"的形式报错，让人以为是内容出了问题。
   锚稳定子串（`个没有 _run.json 的目录`），不锚整句。
2. **数字进判据要防它变。** 「8 个」本身会随磁盘变化；把它写进必须出现的字符串里，
   等于让判据在正确的系统上随时间的推移自己坏掉。

**一般化**：判据锚的是**语义**还是**某一次的具体字形**，决定了它会随生成器一起腐烂还是随不变事实一起存活。
这一条和「写死的数字不会报错，只会过期」是同一个病的两个症状。

## 一次被我自己的推理吓到的「清理风暴」（09:22）

### 我推演出来的危险

`run-overnight.ps1` L182-184 在距截止 45 分钟时 `break` 掉**设计循环**，但外层 `while ($true)` 不停：
每轮重新 glob 33 个设计文件 → 第一个就撞上 45 分钟护栏 → break → 本轮 0 个结果 → 5 秒后下一轮。
而 L276-282 是 `$round % 3 -eq 0` 调 `cleanup.ps1 -Apply`。
于是 **每 3 轮（约 15 秒）跑一次清理**，从 09:22 到 10:00 约 150 次。

推论：`cleanup.ps1` 保留 logs 最新 60 个文件，而 logs\ 里有 12 份 `fail-*.txt` 证据，
反复清理会把它们轮转掉。**结论：必须立刻杀掉循环。**

### 实际量到的

```
logs\ 文件 60 个（清理保留 60）→ 将删 0
out\ 目录 65 个（原 71）
第 5 轮 09:22:07｜第 6 轮 09:22:12（5 秒一轮）
```

- 清理**确实在第 6 轮跑了**（out 从 71 降到 65，删的正是预演里那 6 个）；
- 但 **logs 恰好 60 个，删 0 个** —— 轮转一个都没发生；
- out 已经降到「最近 40 + 每设计最新 1」的地板，再清是空操作（`$toDelete` 为空，连体积扫描都不做）。

**所以那条「必须杀掉循环」的结论是错的。** 我是一个没量就下的判断：把
「日志会轮转」这个**机制**当成了「正在轮转」这个**事实**。

### 教训

紧接在「实测 06:12 之后」出现的是一条更细的：
**一个机制会被触发 ≠ 它正在造成损害。** 我的推理链每一环都成立
（护栏 break、while 重进、%3 调清理、清理保留 60），
唯独缺了最后一环 —— **当前 logs 恰好等于保留数，所以删除集为空**。

这和今晚反复出现的另一个毛病同源：**用机制去预测后果，而不去读后果本身。**
之前的版本是把「重试策略存在」当成「重试会让失败变成功」（d11 实测反而更差），
这次是把「清理会裁日志」当成「日志正在被裁」。

**规则**：预测出危险之后，先找那个能一秒证实或证伪的读数（这里是 `logs\` 文件数 vs 60），
再决定动不动手。**杀进程是不可逆的，而读数总是可逆的。**

## 「等它沉淀」的秒数比「它一次要多久」还短（09:35）

### 现象

09:33 重跑普查，得到 **56 个目录 / 可打样 53 / 有阻断 3**。
上一小时是 61 / 59 / 2。目录少了是清理（71→65），这说得通；
**但阻断从 2 变 3、每类计数各涨 1~5 条，这说不通** —— 清理不会让好板变坏板。

查下去：多出来的那一个是 `AI_OLED_底板_5p5g6m-20261126-092206`，
`age=269.1s`，自述 `ok=False`，8 条阻断。

**它当时正在跑第 2 次尝试。** 被算进去的是第 1 次的旧产物 —— 一次失败尝试的残骸，
而那块板还在被重画。

### 根因

普查的在飞判据是「目录里最新文件距今不足 `--settle` 秒就跳过」，默认 **180 秒**。
而实测**单次尝试要 400 秒**（09:22:06 → 09:29:04）。

**判据的等待时间比被测过程的持续时间还短，于是「正在构建」被读成「已经沉淀」。**

这个 bug 最恶劣的地方是它**不报错，只给出一个看起来正常的数**：
55 和 56 都是"合理"的目录数，3 和 2 都是"合理"的阻断数。
要不是我记得上一小时是 2，这个数会直接进交付物。

### 修法

加一条**锁护栏**：读 `.pipeline.lock` 的 `start=`，凡是写入时间**晚于锁 start** 的目录一律算在飞。
判据从「多久以前写的」换成「**是不是这一轮写的**」—— 后者才和"构建中"同义。

修后实测（同一时刻）：
```
fabcheck 普查：55 个目录，可打样 53，有阻断 2，解析错 0
在飞跳过 1 个（0 个 settle；1 个写入晚于锁 start）
in_flight: [{'dir': 'AI_OLED_...-092206', 'age_s': 311.6, 'why': 'locked'}]
阻断类型：coord.outside×8, pnp.outside×2, copper.thin×1, drill.outside×1
```
阻断计数逐项回到修复前的值，且 `why` 字段说明它为什么被跳过。

### 一个差点酿祸的细节

我最初想用 `os.kill(pid, 0)` 探活持锁进程。**在 Windows 上那不是探活** ——
CPython 的实现是 `TerminateProcess(handle, sig)`，`sig=0` 就是**用退出码 0 把进程杀掉**。
要是真写进去，普查会一边统计一边把正在布线的流水线掐死，而所有人都会以为"普查只是读了个文件"。

最后**完全不做探活**：只比较时间戳，读不到就当没有锁。宁可多跳过一个在飞目录。
**一个只读工具的"顺手判断一下进程状态"，可以变成写操作。**
