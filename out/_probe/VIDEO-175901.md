## 2. 去重：sha256 内容哈希 + 相邻合并

规则：
1. 按 `目录名` 升序、`文件名` 升序串成一条序列；
2. 对每个 PNG 读字节算 `hashlib.sha256`；
3. 与**上一个被保留的帧**哈希相同 → 丢弃（「相同相邻帧合并」）；
4. 若某目录所有帧全被判重复，仍保留其**第一帧**，保证该阶段在视频里存在过。

| 指标 | 数值 |
|---|---|
| 总帧数 | **202** |
| 唯一帧数（合并后序列长度） | **126** |
| 被合并（重复）帧数 | **76** |
| 重复率 | **37.62 %**（76/202） |
| 202 个文件的「不同内容」种类 | **65** |

> 65 < 126 说明：合并只吃掉**相邻**重复，同内容但不相邻的帧（各目录都会重新从 `sch-wired` 开始）仍在序列里——所以 126 是「相邻去重后的状态序列」，不是「全局不同图像数」。

各目录明细（相邻对 = 帧数−1）：

| 目录 | 帧数 | 保留(唯一) | 相邻对 | 其中内容变化 | 其中完全相同 |
|---|---|---|---|---|---|
| `1-smart-fit` | 66 | 46 | 65 | 45 | 20 |

- **「整目录全重复」未发生**：4 个目录都贡献了独有帧，所以 §2 的第 4 条规则这次没触发（保留首帧的兜底逻辑已实现但未使用）。

## 3. 生成视频

### 3.1 归一化（源帧尺寸不一致 + 奇数宽）

- 主尺寸 `737×434`，但 **737 是奇数**，H.264 + `yuv420p` 要求宽高均为偶数，否则 `libx264` 直接报 `width not divisible by 2`。
- 处理：统一铺到 **`738×434`** —— `737×434` 的 198 张只在右侧**复制最后 1 列**（视觉无差），`1000×410` 的 4 张按比例缩到 `738×303`、用该帧自己的左上角底色（`#FFFCF8`，原理图白）上下留白居中（上下各 65 px）。
- 归一化用 Pillow 落盘到临时目录，ffmpeg 侧只处理同尺寸输入，避免 `scale/pad` 与 `concat` 在滤镜图里争尺寸（实测会报 `Padded dimensions cannot be smaller than input dimensions`）。

### 3.2 命令

单次 ffmpeg、126 个输入、滤镜图写文件（避开 Windows 命令行长度与引号转义）：

```
C:\ffmpeg\bin\ffmpeg.exe -y -nostdin -hide_banner -loglevel warning -stats ^
  -framerate 30 -loop 1 -t 0.8 -i <帧1>.png  ... (共 126 组) ... ^
  -/filter_complex F:\cache\temp\v175901\graph.txt -map "[vout]" ^
  -c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p -r 30 -movflags +faststart ^
  out\video-175901.mp4
```

`graph.txt` 每路一条链，最后拼接 + 锁帧率：

```
[0:v]setsar=1,format=yuv420p,drawtext=fontfile='C\:/Windows/Fonts/msyh.ttc':
     textfile='F\:/cache/temp/v175901/labels/0000.txt':x=8:y=8:fontsize=20:
     fontcolor=white:box=1:boxcolor=black@0.65:boxborderw=6[v0];
 ... (共 126 条) ...
[v0][v1]...[v125]concat=n=126:v=1:a=0[vc];
[vc]fps=30,format=yuv420p[vout]
```

要点：
- **每唯一帧 0.8 s**（可读性下限），`-framerate 30 -loop 1 -t 0.8` ⇒ 每帧正好 **24 帧**；126 × 24 = **3024**，126 × 0.8 = **100.8 s**，与 `ffprobe` 实测一致（见 §4）。
- 标签用 `drawtext` 叠加在**左上角**，内容 `<目录名>/<文件名>`（如 `4-expand-1.25x-retry2/0042-pcb-drc.png`）。字体 `C\:/Windows/Fonts/msyh.ttc` 存在已确认；`ffmpeg -filters` 确认有 `drawtext`。
- 文本走 `textfile=`（不把中文/斜杠塞进滤镜表达式）；路径里的 `:` 已转义为 `\:`，否则 `F:/cache/...` 会被当成 `textfile=F` + 未知参数报 `No option name near '/cache/...'`。
- `-pix_fmt yuv420p` + `+faststart`：保证常见播放器/网页能打开。

## 5. 这些帧证明了什么 / 没证明什么

### 5.1 证明了

1. **画布在那个时刻确实渲染出了那个状态。** 每帧是 `getCurrentRenderedAreaImage()` 的真实输出，不是重绘/合成；视频里能依次看到 `sch-wired → pcb-imported → pcb-layout → pcb-pour → route2 → route → pcb-routed → pcb-bottom → pcb-stitched → pcb-clearance → pcb-patched → pcb-drc` 四个目录各一遍。
2. **同一 AI 流程被跑了 4 次（4 个目录），同阶段画面高度可复现。** 按阶段名跨目录比（每阶段 6 对）：`2`/`3`/`4` 三个 expand 目录之间只差 **0.000%–0.011%**（`pcb-imported` 上 2↔3 是 **0.000%**，`pcb-routed` 上 2↔4 是 **0.005%**），而 `1-smart-fit` 与它们差 **9.47%–16.28%**。即 retry 阶梯的三次重跑在画布上渲染出的是**同一个**板状态，smart-fit 那次是另一个——**这一条只在「渲染出来什么样」的层面成立**，谁对谁错画布判断不了。
3. **成片不是单帧循环。** 126 个唯一帧、3024 个视频帧、7 抽帧 21 对全部不同且 21 对全部 ≥1% 像素变化（§4.2）。
4. **真实画面变化确实存在**：相邻唯一帧的 125 个转移里 **31 个 ≥5% 像素变化**（如 `sch-wired→pcb-imported` 100%、`pcb-routed→pcb-bottom` 17.25%、`pcb-bottom→pcb-stitched` 17.25%），不是「只有一个进度数字在动」。

### 5.2 没证明（重要）

1. **只证明「画布渲染出了这个状态」，不证明「这个状态是正确的/可制造的」。** `pcb-drc.png` 只说明 DRC 的结果被画到了画布上，**不说明 0 violation**；`route*.png` 只说明布线画面被渲染出来，**不说明网络真连通、线宽/间距/过孔环合规**；`pcb-stitched` 不说明缝合过孔真的覆盖了地平面。这些要另外的网表/DRC/几何证据，画面不能替代。
2. **不证明 AI 的决策是对的。** 画面只记录「做了什么」，不记录「为什么这么做」，也不记录被回退/被放弃的中间尝试（那些没进帧的步骤不可见）。
3. **不证明帧序列连续。** 抽帧是脚本按固定间隔抓的，两次抓帧之间的动作完全不可见；0.8 s/帧是**人为保持时间**，与真实耗时无关。
4. **文件名里的 `t6s`/`t403s` 不是画面里的时钟。** 它是脚本记录的耗时，画面本身没有时间戳；不能用它反推真实工期。
5. **126 个「唯一帧」里有相当一部分画布其实没变。** 这是本次最该说清的一条：
   - 相邻唯一帧 125 个转移中，**88 个像素变化 <0.1%**（画布静止，只有画面上一小块区域在动：实测 `1-smart-fit` 某对 737×434 帧间仅 158 个像素不同），2 个 1%–5%，4 个 0.1%–1%，**31 个 ≥5%**；
   - 若把「与上一保留帧差异 <1% 像素」也视为重复，126 帧只剩 **34 帧**（27.2 s）。
   - 也就是说：**视频「不是静止的」这个证明成立（有 31 处真实变化），但「每一帧都是新状态」不成立。** 按 sha256 去重得到 126，是**字节层面**的唯一，不是**视觉层面**的唯一。
6. **不证明没有重复内容跨目录**：202 个文件只有 65 种不同内容，四个目录大量复用同一批画面（尤其四个 `0000-sch-wired` 里 `4-expand-1.25x-retry2` 那张只有 13109 B，明显与其余三张 71 KB 的不同，可能是加载中的半成品画面——画面本身不能判断哪个「对」）。
