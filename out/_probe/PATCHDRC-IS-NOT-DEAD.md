# patchDrc：不是死代码，但性价比很差（14–17 s 换 0 处修复）

> 实测 2026-11-27。分母：`out/*/\_log*.json` 共 **188** 个日志文件（其中只有最新一轮带 `ms` 遥测）。

## 审查者的两条判断都不准

| 审查说 | 实测 |
|---|---|
| 「`patchTotal` 恒 0」 | 分布是 `{0: 186, 2: 1, 3: 1}` —— **不是恒 0**，有 2 条非零 |
| 「patchDrc 累计 0.0s」 | 最新的那一轮 3 次尝试分别 **17.5 s / 14.2 s / 14.2 s** |

（第二条大概是读到旧日志里没有 `ms` 字段，把「没有读数」当成了「0」。）

## 它到底在干什么（全语料 `patch*` 事件计数）

```
patchPairSynth      1363
patchTooFar         1244      ← 主导：候选节点太远，放弃
patchTotal           188
patchDone            124
patched              118      ← 真的创建了图元
patchRound            67      ← 只在有断连时才跑
patchVerify           34
patchNoProgress       33      ← 补了但复检没有净收益
patchReverted         31      ← 整轮回滚
patchPerErr            7
patchRoundNet          3
```

**它不是在空转**：试了 1363 次配对、真的创建了 118 次图元、回滚了 31 次。
问题是**「距离上限」拒掉的比修好的多一个数量级**（1244 vs 118），
而最终记账 `patchTotal` 几乎总是 0。

`patchRound` 全部是 `round: 0` —— 后两轮从未进入。这与审查者的观察一致，但原因不是死循环，
而是第 0 轮就判了 `patchNoProgress` / `patchReverted` 然后 break。

## 代价与收益

- **代价**：14–17 s / 次尝试（一次运行里最多 3 次）⇒ 约占整轮 350 s 的 8–9%；
- **收益**：`patchTotal > 0` 只出现过 2 次（2 处、3 处）。

也就是说这是一个**「花 30 秒保证一件事（连通性兜底）」**的环节。连通性漏了会导致
DRC 报 Connection Error（现在是硬阻断），所以不能因为它「多半修不到」就删掉。

## 我没有改它，原因

提高 `patchTooFar` 的上限看起来很自然，但代码注释里记着这条上限的**来历**：

> 旧实现取「离断点最近的同网节点」与「第二近的同网节点」，而第二近的可能在板子另一头
> （d6 实测 400 mil），于是在底层拉一条贯穿整板的长铜：补前 2 处违规 → 补后 21 处，
> 19 处是它自己造的。

放宽上限就得重新验证「补铜会不会造出更多违规」。我没有那批受影响语料的可比基线，
**所以只记录，不改**。

## 可复用的判断

- 「最终记账恒为 0」不等于「没在干活」——中间事件（`patchPairSynth` / `patched` /
  `patchReverted`）才是它在干什么的证据。只看终点会把「一直在试、一直在回滚」误判成死代码。
- 「没有 `ms` 字段」不等于「耗时 0」。把缺读数读成 0，是这个项目反复出现的一类错。
