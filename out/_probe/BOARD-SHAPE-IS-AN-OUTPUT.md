# 这块板子的形状是**算出来的**，不是**选出来的**

测量于 2026-11-26T22:0x+08:00，对象 `designs/mic-esp32s3-v5.json`（sha256_12 `AD6CCBDFDC22`），
分母 = 该文件的 `_placement` 里 28 个器件全部 + `boardWidthMil/boardHeightMil` 两个字段。
尺寸表见 `scripts/audit-placement.mjs` 的 `SIZES`（按 LCSC 实测，不是标称）。

## 一、用户的原话和它对应的量

> 「你没有考虑天线上面不能有任何元器件的遮挡……你也只是选择了一块板子，
> 然后在上面铺满元器件。你并没有合规的去摆放这些元器件，比如说根据基板的形状
> 来决定元器件怎么摆放，就是你要综合综合考虑各种影响来画板子。」

这句话里有四个可以分开检验的指控。前两个已经落地（天线净空、声孔净空），
第三个「随便选一块板子然后铺满」这次才量：

| 指控 | 可算的量 | 实测 |
|---|---|---|
| 天线被遮挡 | 天线净空带内有无器件 | 已修：`antennaKeepout.intruders=[]`，`padsInBox=0` |
| 铺满一块随便选的板 | 器件云包围盒 / 板框 | **91.1% × 102.8%** |
| 板子形状没被当作输入 | 板框尺寸的来源 | 板框 = 器件云 + 几十 mil 余量 ⇒ **形状是输出** |
| 没按板形状摆件 | 摆放是否响应板框变化 | 未测（需要一次板框变量实验） |

## 二、实测数字

```
板      1300 × 3700 mil = 33.0 × 94.0 mm    面积 3103 mm²    长宽比 2.85:1
器件    28 个，封装体面积和 924 mm² = 板面积的 29.8%
器件云  包围盒 x[36,1220] y[-3831,-26]  跨度 1184 × 3805 mil  占比 91.1% × 102.8%
余量    左 36 mil / 右 80 mil / 上(y=0 侧) 26 mil / 下 = 天线悬出 131 mil
```

`102.8%` 不是算错：`y=-3831` 是 U1 的天线尖端，按设计**故意**悬出板边 131 mil
（`antennaKeepout.overhangMil=261` 是相对标称板边 −3700 的量，与这里 −3831 的口径差
正是 3700−3831 = −131，即悬出量；两个数字同源，不要混读）。

按面积排前几名（mil² / mm²）：

| 位号 | LCSC | 尺寸 | 面积 | 位置 |
|---|---|---|---|---|
| U1 | C2913199 | 748×1030 | 770440 / 497.1 | `(650, −3316)` |
| USB1 | C165948 | 329×388 | 127652 / 82.4 | `(200, −220)` |
| U2 | C6186 | 362×268 | 97016 / 62.6 | `(700, −2780)` |
| H1 | C49023793 | 305×284 | 86620 / 55.9 | `(650, −2350)` |
| U5 | C2912107 | 189×205 | 38745 / 25.0 | `(650, −1720)` |
| SW1-3 | C2832146 | 128×217 | 27776×3 / 17.9×3 | `y=−900`，跨距 702 mil |

U1 一个人占 497 mm² = 板面积的 **16.0%**，而且 748×1030 的封装决定了板宽不能小于
748 + 两次焊盘逃逸余量。这是硬约束，不是选择。

## 三、结论：方向被反了

### 3.0 先钉一个比长宽比更硬的事实：摆放**根本不读**板框

`scripts/relayout.mjs` 里 `W` 和 `H` 从 L200 读进来、L201 校验、L288-289 用它们
**判断越界**。除此之外，`BANDS`（L51-161）里每个器件的 `x`/`y` 都是**写死的绝对值**
（`U4 x:650 y:-200`、`USB1 x:200 y:-220`、`SW1 x:299`、`SW2 x:650`、`SW3 x:1001`……）。

也就是说板框对摆放的作用只有一种：**事后否决**（越界就 exit 1），从不参与推导。
把 `boardWidthMil` 从 1300 改成 1625，除了让越界判定变松，**不会移动任何一个器件**。

这不是「按基板形状摆得不好」，是**这个依赖在结构上不存在**。
用户说「根据基板的形状来决定元器件怎么摆放」，指的就是这条缺失的边。

唯一会移动器件的机制是 `separate()`（L233-276）：发现相交就把一对各推开 6 mil，
沿重叠更薄的那个轴。它是个**消重叠**的局部修补，不看板框、不追求任何布局目标
（不居中、不均衡、不留空白）。所以即使板子加宽，器件也只会保持原来那一列，
直到分离逻辑不再需要推 —— 宽度余量最终变成**板边的空白**，不是更合理的排布。

### 3.0.1 这条依赖现在已经补上了（`relayout.mjs` sha `14CD364ECE70`）

给 `BANDS` 的器件加了可选的 `hz`（水平意图），把「这个器件在宽度方向上属于什么」
写成显式的一种，而不是一个写死的数：

| `hz` | 含义 | v5 里谁用它 |
|---|---|---|
| `'center'` | 功能上属于正中，跟着板中线平移 | U1/U2/U3/U4/U5/H1/SW2/R2/R3 |
| `{of,dx}` | 没有独立位置，意义是「贴着某一颗」 | C4/C5/C6/C7/C1/C2/C3/C8/D1/R1/R4/R5 |
| `'edgeL'`/`'edgeR'` | 属于**这条边**（连接器口面），宽度变化不该动它 | USB1 |
| `'spreadL'/'spreadR'` | 属于**在宽度上均布**（拇指区按键） | SW1/SW3/SW4/SW5 |
| 缺省 | 绝对坐标，不动 | 无（26 个全部标了） |

实测响应（同一基准只改 `boardWidthMil`）：

| 板宽 | 随板宽移动 | 不动的 |
|---|---|---|
| 1300 → 1500 → 1625 | **23 / 26** | R4、R5、USB1 |

不动的 3 个是 USB 簇：USB1 用 `edgeL` 锚在左边缘，R4/R5 用 `{of:'USB1'}` 跟着它，
所以整簇对宽度变化不响应 —— **这是正确行为**，不是遗漏。贴边的东西不属于坐标。

**回归不变量**：W=1300 时，改动前后的 `relayout.mjs` 必须在同一基准上输出
逐器件逐字段全同。实测 `26/26`，`x/y/rot/lock` 差异 0。做法是把改动反向重建出
旧版（sha 必须逐字节回到 `F73D3989773C`，否则拒绝写盘），两版各跑一遍再比。
**不能拿设计文件当基准** —— 设计文件里 C5 的位置和 `BANDS` 已经不一致（见 3.0.2），
用它当预期会把一处真实的过期当成补丁的回归。

### 3.0.2 顺带量出的两处过期（不是补丁引入的）

1. **`BANDS` 里 C5 在 IMU 带 `(1000,-1720)`，设计文件里 C5 在 AMP 带 `(860,-2160)`。**
   设计文件是对的：AMP 带注释说「功放自己的电源去耦由 C5 就近承担」，实测 C5 左边到
   U3 右边 **79.5 mil**，与注释的「79 mil」吻合；而它到 U5 右边是 56.0 mil（不同带）。
   若有人今天对 v5 跑一次 `relayout.mjs`，C5 会从功放旁边跳回 IMU 带 ——
   U3 的 3V3 去耦就此离开 79.5 mil 变成 300+ mil，而 DRC 不会报任何错。
2. **`relayout.mjs` 的计划表只有 26 个器件，v5 有 28 个**（C9/C10 是后加的）。
   它自己的完整性检查会 `exit 2`：「计划里没有: C9, C10」。也就是说这个工具
   **今天对 v5 根本跑不起来** —— 值得庆幸的是没有脚本在流水线里调它，
   否则它会把 C5 挪走再失败。

### 3.1 板宽 1300 的来历

板宽 1300 的来历是「最宽的那个器件 748 + 两侧余量」，板长 3700 的来历是
「把 28 个器件排成一列需要的长度」。两个方向都是**器件推出来的**。

于是必然出现三件事，而且都是结构性的、不是这一次没摆好：

1. **长宽比 2.85:1**。28 个器件沿一条轴排开，长度自然被撑开。想让比例合理，
   必须允许器件**换列**，而 `relayout.mjs` 的 `BANDS` 是按 y 分带的一维结构
   （IMU 带 `y=−1720`、AMP 带 `y=−2100`、按键带 `y=−900`……），它天生只会排一列。
2. **「铺满」是真的**：器件云在 x 方向占 91.1%、y 方向占 102.8%。板子没有任何
   可用来做机械、握持、装配的空白。用户看到「铺满」不是错觉。
3. **加宽是被动的**：`run-all.ps1` 的重试阶梯里 `expand-1.25x` 在契约检查失败时
   把 `W 1300 → 1625`（只加宽、不加长，因为天线在下边缘）。也就是说，
   宽度的最终值由**某一次失败**决定，而不是由设计意图决定。

一个手持有线/无线麦克风的板子该是什么形状，是**产品决定**：手掌宽度大概 60–75 mm，
所以 33 mm 宽是合理的（单手可控），94 mm 长偏长但可接受（比一支笔短）。
问题不在具体数字，在于**没有一个地方写着「这块板必须是多大」，而器件摆放要服从它**。

## 四、这条要怎么变成判据（不改板子，先立尺）

新增设计字段 `_formFactor`：

```json
"_formFactor": {
  "declaredMil": { "w": 1300, "h": 3700 },
  "why": "……凭什么这两个数（握持宽度 / 可装配长度 / 外壳内腔）",
  "toleranceMil": 0
}
```

然后两条判据（都纯从设计文件算得出来）：

- `board_shape_declared`：设计文件里有没有独立于器件的板框意图。
  **没有 ⇒ `unknown`（退 2），不是 pass** —— 「板框是器件推出来的」这件事
  和「板框被验证过」不是同一个结论，不许混。
- `placement_follows_formfactor`：声明了之后，器件云必须落在声明的板框内
  （留出天线悬出这类显式豁免），且**任何超出都必须由某个保留区解释**
  （天线带 / 声孔 / 连接器插拔空间 / 握持区）。没有解释的越界就是缺陷。

阈值不写死：容差来自 `toleranceMil`，越界的「解释」来自设计里已有的
`_antennaKeepout` / `_copperVoids` / 连接器朝向，全部是已声明的事实。

## 五、为什么这次不直接改

两件事挡住了，都不是技术问题：

1. **改板框要改 `designs/*.json` 的 `boardWidthMil/boardHeightMil`，而这个文件在构建
   启动时被读**。当前有一轮构建在跑（`out\ESP32S3_Wireless_Mic_V5-20261126-214236`）。
   改它等于让这一轮的产物和设计文件不对应。
2. **换列需要改 `relayout.mjs` 的 `BANDS` 结构**（从一维分带改成二维网格），
   而板框尺寸、净空区、连接器朝向都要一起参与 —— 这是一次真正的布局器重构，
   不是调参。半途改会让「DRC 叶子从 5 降到多少」这个正在进行的测量失去可比性。

所以这一轮先立尺，下一轮按尺改。顺序不能反：**先有「板框是输入」这个约束，
再有用它去驱动摆放的布局器**。反过来做就是又一次「先摆了再说形状」。
